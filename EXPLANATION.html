Technical Architecture Deep-Dive

1. Why Feature-First over Layer-First?

Traditional layer-first architecture groups code by technical responsibility (views/, controllers/, models/). As an application grows, modifying a single feature requires hunting across disconnected folders.

In Feature-First (features/auth/, features/item/, features/claim/), all business logic, UI, and domain models related to a single capability live together. This modularity reduces cognitive load, enables independent refactoring, and matches how engineering teams divide work.

2. State Management Strategy (Riverpod 3)

  • Compile-time Safety: Global constants analyzed at compile-time eliminate runtime ProviderNotFoundException.
  • Modern Notifiers: Replaced deprecated StateProvider with Riverpod 3 Notifier and AsyncNotifier, cleanly organizing mutations into small, testable methods.
  • Computed Selectivity: filteredItemsProvider watches itemsStreamProvider, selectedTypeFilterProvider, selectedCategoryFilterProvider, and searchQueryProvider. It only recomputes when one of those specific dependencies emits a change.

3. Privacy-First Campus Model

In typical lost & found boards, users post exact phone numbers and specific serial numbers publicly, exposing victims to extortion and scam callers. Finders Keepers solves this through:

  • Approximate Locations: Public listings only reveal fuzzified campus landmarks (e.g. "Main Library • 3rd Floor"), never exact desk coordinates.
  • Hidden Identifiers: Distinguishing marks and serial numbers are stored as private verification questions that claimants must answer before contacting the finder.

Interview Preparation Guide

Q1: How does Riverpod's computed Provider optimize list filtering performance?
Answer: filteredItemsProvider is a pure derived provider. By watching individual filter notifiers (type, category, query) and the data stream, Riverpod caches the filtered list. If unrelated UI rebuilds happen, the filtering calculation does not run again. Widgets consuming ref.watch(filteredItemsProvider) only rebuild when the output list actually changes.
Q2: Why program against an abstract ItemRepository instead of direct Firestore calls?
Answer: It decouples the UI from network infrastructure. By introducing ItemRepository, we can test feed pagination, search filtering, and error states using InMemoryItemRepository in 5ms without network calls. When connecting to production Firestore, we simply implement FirestoreCustomItemRepository implements ItemRepository without modifying any screen or widget code.
Q3: How do you handle reactive authentication redirect guards in GoRouter?
Answer: GoRouter receives Riverpod's authStateChangesProvider in its top-level provider definition. When the auth stream emits a user or null, GoRouter re-evaluates its declarative redirect callback. If an unauthenticated user enters /home, it redirects to /login; if an authenticated student visits /login, it immediately redirects them to /home.
